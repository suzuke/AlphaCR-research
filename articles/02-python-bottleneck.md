# 訓練太慢，該先加速哪裡？

**一句話：要讓 AI 能練更多場，先量整條流程的耗時；這次瓶頸在引擎外圍的 Python，優化後每局處理器時間從 14.5 秒降到約 10 秒。**


> AlphaCR 技術筆記 02。只談想法與教訓，不談實作細節。

## 背景

強化學習需要大量對局。我們的資料產生流程裡，每一局都要花掉相當多的 CPU 時間，整個訓練的牆上時間幾乎被它決定。所以效能優化是長期議題：每省下一點，所有後續實驗都會跟著受益。

## 直覺是錯的

一開始我們的假設很自然：遊戲引擎在做大量的單位運算，所以引擎應該是最慢的部分。於是計畫的第一步是想辦法讓引擎本體更快。

這個假設沒有經過量測。真正量了之後才發現，引擎本身其實不是大頭。大量時間花在 Python 這一側，也就是圍繞在引擎外面的那層黏合與協調程式碼。引擎在算的時候，Python 常常在忙別的事，或是在等。

## 數字

優化之後，每局的 CPU 時間從 **14.5 秒降到約 10 秒**，整體流程快了 **1.44 倍**。

![每局 CPU 時間](../figures/cpu_per_game.png)

這個數字不算驚人，但有兩點值得注意。其一，它是端到端的數字，不是某個微基準測試上的漂亮分數。其二，我們把「不改變任何模擬結果」當作優化的前提，也就是前一篇講的決定性檢查必須維持通過。優化如果會改變結果，就不能算優化。

## 學到的事

**1. 先量，再動手。** 我們花時間最多的地方，不是我們以為的地方。如果當初直接去改引擎，會花掉幾週，換來幾乎看不見的改善。

**2. 「快的語言」不等於「快的系統」。** 系統的速度取決於最慢、而且沒被注意的那一段。把熱點的運算放在高效能的部分沒有錯，但如果周圍的黏合層很笨重，整體還是被它拖住。

**3. 優化要有安全網。** 沒有可重現的驗證，任何優化都只能憑感覺說「應該沒壞」。有了逐 tick（遊戲更新一步）的比對，我們才敢大膽重構，因為壞了會立刻知道。

**4. 1.44 倍也很值錢。** 訓練是上百個迭代、上萬局的規模。1.44 倍意味著同樣的時間可以多跑近一半的實驗，或是把一個週末的訓練縮短成一個晚上。小幅度的效能改善，在重複次數夠多的流程裡會被放大。

## 一個更大的提醒

這件事讓我們修正了一個工作習慣：在決定優化目標之前，先寫下「我認為瓶頸在哪裡」，量完之後再對答案。一開始我們的猜測錯得相當徹底，而這種錯誤只有在把猜測寫下來、和量測並排比較時才會被看見。如果沒有這個對照，人很容易事後覺得「我早就知道」，下次還是會憑感覺行動。

另一個副作用是團隊的注意力被重新分配。原本大家預期要深入引擎內部做大工程，結果更值得投資的地方是外圍那層看起來不起眼的程式碼。不起眼的地方，往往也是最少人檢視的地方。

## 如果重來一次

我們會在專案最早期就放進一個簡單的耗時分解，每次大改動後自動更新。不是為了追求極致，而是避免再次「憑感覺」決定該優化哪裡。優化最貴的不是寫程式的時間，而是花在錯誤目標上的時間。
